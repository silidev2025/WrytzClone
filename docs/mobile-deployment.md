# Mobile testing deployments

Mobile apps now have **Publish & test on a phone** in the editor's Publish dialog. Choose **Android APK** or **iOS live tunnel**. The draft must save successfully before publication. Publishing and queueing the test happen in one transaction, with a revision check to prevent publishing an older draft.

Both options wrap the existing published web app. They preserve its server-side login and data rules and need an internet connection. A build's revision records the design that was published when the build was requested; it is **not an immutable copy**. Future publishes change the content in existing wrappers. Changing the published slug stops old deployments; create a new APK/tunnel for the new address.

## Operator setup

1. Host Craftbase and its published apps on working public HTTPS addresses. Set `CRAFTBASE_PUBLIC_URL` to the main origin, for example `https://craftbase.example.com`. If using `NEXT_PUBLIC_ROOT_DOMAIN`, its app subdomains must also resolve and have valid HTTPS certificates. Localhost is not reachable from clients' phones. An Expo tunnel transports the iOS shell; it does not expose the Next.js web server.
2. Generate a secret with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Set it as `CRAFTBASE_MOBILE_WORKER_TOKEN` on both the server and worker. Never use a `NEXT_PUBLIC_` variable for it. Restart the web server after setting these server variables.
3. Use one persistent worker machine with Node.js **22.13 or newer** (for Expo SDK 57), JDK **17 or newer**, and Android SDK **platform 35** plus stable SDK build tools. Android Studio's SDK Manager can install them. Set `ANDROID_HOME` and `JAVA_HOME` if they aren't detected; JDK commands must otherwise be on PATH. The worker supports Windows, macOS and Linux. It is separate from the Next.js request process and cannot run inside a serverless function.
4. On the worker, run `npm ci` in the project root. For iOS, install and start Docker with Linux containers, then run `docker build -f mobile/expo/Dockerfile -t craftbase-expo:local .`. Set `CRAFTBASE_EXPO_IMAGE` if using another image tag. The image installs Expo from its separate pinned lockfile. `npm run mobile:install` alone no longer enables public iOS tunnels. Android compilation still uses the host SDK and private signing-key directory.
5. Set `CRAFTBASE_MOBILE_SERVER_URL` if the worker uses a different origin to reach the server. A local worker can use `http://localhost:3000`; remote connections must use HTTPS. Configure the worker's environment or `.env.local`; the script loads the project env file. No database credentials are needed on a separate worker.
6. Run `npm run mobile:worker` and keep it running under a process supervisor. On Windows, run it in a terminal or a background service. The worker advertises only installed capabilities. Android and iOS choices explain when setup or an online worker is missing. One worker processes one APK build and up to two iOS sessions at once. Extra requests wait in the queue. Run only one worker per Craftbase deployment.

Tunneling uses Expo/ngrok and requires an internet connection. Each public Metro process now runs in a disposable container with a read-only root filesystem, a bounded temporary filesystem, no host mounts, an unprivileged user, and CPU/memory/process limits. Only the public job id, app name and URLs are passed to it. Android keys, database credentials and worker tokens stay outside the container. The Docker build context excludes everything except the wrapper, pinned package manifests and tunnel helpers. Keep Docker and the base image patched. This adapter currently uses anonymous Expo tunneling; host Expo login/token configuration is not forwarded into containers.

## What clients receive

- **Android:** a signed, non-debuggable APK for Android 8+ with the app's name and a generic Craftbase launcher icon. Each app has a separate package name and signing key, so later test builds can update the same installation. Download access requires the app owner's Craftbase session. The owner can transfer the downloaded APK to testers; recipients must allow installation from their browser/file manager when Android prompts. The APK uses an Android WebView, supports back navigation, file selection, loading failures and retry, respects system insets, blocks cleartext and mixed content, and opens external links in the device's browser. It includes no session tokens, database contents or server secrets.
- **iOS:** an Expo Go link and a QR code generated locally in the browser. Install the current compatible Expo Go from the App Store, then scan the code with iPhone Camera or open the link on the phone. The worker bundles the shell and checks the public tunnel before reporting it ready. This is an Expo Go preview, not an IPA or TestFlight distribution. No Apple provisioning is performed. The link is public to anyone who receives it; app login and data permissions still apply. The session lasts at most one hour and requires the worker to remain connected.

Store signing, store review, payments/push integrations, and native device permissions beyond the wrappers' current capabilities are separate work. Camera capture, microphone, location, and JavaScript-generated blob downloads are not added by this workflow. Browser download links may open the system browser, which has its own login session.

## Lifecycle, storage and recovery

- Builds are durable records in the existing JSON/Postgres store. Worker authentication uses a dedicated bearer secret, with a separate random lease for each claimed job. Clients can list, stop, and download only their own app's deployments. API responses omit leases and worker credentials.
- Pending jobs time out after 10 minutes; builds after 15 minutes. Heartbeats renew a 90-second lease. A disconnected worker produces a failed or expired state instead of a permanent spinner or a stale launch link. Stop/cancel is observed on the next heartbeat, normally within 30 seconds. An already installed APK or loaded WebView still opens the independently published web app.
- APKs are held in the existing blob store for 7 days; downloads stop when the app is unpublished/taken down or the deployment is removed. Housekeeping removes expired blobs and deployment history after 30 days. Self-hosted servers run bounded maintenance every minute; Vercel uses authenticated `/api/maintenance` with `CRON_SECRET`. The included daily cron is a fallback: schedule it every 1–5 minutes for active deployments and monitor the persisted `maintenance_status` job. App/account deletion queues durable cleanup of artifacts.
- Workers send APKs in retryable 1 MiB chunks, with lease ownership and per-part/full-file SHA-256 checks, then finalize the existing artifact. The APK limit remains 20 MiB. Downloads stream bounded reads and support HTTP byte ranges. Normal design/attachment uploads now have a 4 MiB limit; JSON request bodies are capped at 4,000,000 bytes.
- `CRAFTBASE_MOBILE_WORK_DIR` defaults to `~/.craftbase-mobile`. Temporary job directories are removed after completion or stop. A forcibly terminated worker may leave job directories behind; remove these only while the worker is stopped. Keep this directory outside OneDrive and other cloud-sync folders.
- The worker keeps private per-app signing keys/passwords in `keys/`. Back them up privately. Losing them means the old test app must be uninstalled before installing a build from a replacement key. These files are outside server backups and survive app deletion until the operator removes them. Key filenames use the first 24 hex characters of SHA-256 of the app id. Include key cleanup in the operator's deletion/retention procedure. Never commit or expose this folder through a web server.
- Restrict network access to the worker's local development ports. Only the intended Expo/ngrok tunnel should be reachable by testers. Rotate the shared worker secret if it is exposed. The optional worker services and retention periods should be reflected in the operator's privacy/subprocessor disclosures before enabling them for customers.

## Verification

The 2026-09-29 remediation adds chunk-upload tests and container isolation. Docker is unavailable in the review environment, so the new image/tunnel path has not been built or run there; the older local Expo verification below does not validate the container path. Physical-phone tests and deployed Vercel large-download checks remain necessary. See [the remediation handoff](audit-remediation-2026-09-29.md).

`npm test` runs the existing regression checks. `npm run test:mobile` uses isolated temporary data and checks authentication, ownership, revision checks, unavailable configuration, duplicate publish/claim races, APK delivery, invalid tunnel URLs, cancellation, expiry, unpublishing and cleanup.

APK compilation uses the SDK's [AAPT2](https://developer.android.com/tools/aapt2), D8, zipalign and [apksigner](https://developer.android.com/tools/apksigner), and verifies the signature before uploading the artifact. The iOS adapter uses the documented [Expo CLI tunnel and open endpoint](https://docs.expo.dev/more/expo-cli/) and [Expo Go WebView](https://docs.expo.dev/versions/latest/sdk/webview/). Test on physical Android/iOS devices before customer rollout, especially authentication, file uploads and any external links used by each client's app.

Implementation verification (2026-09-28): TypeScript passed; the production Webpack build passed in an isolated copy with identical source/configuration; all 11 existing regression checks and 10 mobile deployment checks passed. A real signed APK was built, uploaded by the worker, and downloaded through the owner API with the correct MIME type and filename. An actual Expo/ngrok session bundled the iOS shell, passed its public health check, displayed its QR code, and became unreachable after Stop; temporary worker job folders were removed. The publish dialog passed browser checks at 320, 390, 768 and 1440 pixels without page or dialog overflow. A simulated draft-save failure produced zero publish requests. Both dependency audits reported zero known vulnerabilities. These checks used synthetic accounts and data; no real client app was published, and no physical Android/iPhone installation was tested.
